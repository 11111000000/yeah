# yeah-provider — агент Yeah в Paseo

Плагин Paseo, который регистрирует **провайдера ACP** и поднимает ACP-сервер
ядра [Yeah](https://github.com/11111000000/yeah) в Emacs. После установки в
Paseo появляется агент **Yeah** — как любой другой: его выбирают в списке
агентов, и он работает в рабочем каталоге, который открыт в Paseo.

Ядро Yeah — это агентный harness на Emacs Lisp: модель достаётся через gptel,
эффекты идут через реестр инструментов и систему разрешений, а журнал сессии
остаётся append-only JSONL. Провод — ACP (JSON-RPC поверх stdio или поверх
Unix-сокета — см. «Сервисное размещение»).

## Где лежит плагин

**Плагин — часть репозитория ядра:** `plugin/yeah-provider/` рядом с `lib/`,
`tests/` и `docs/`. До 2026-11-18 он жил вне репозитория
(`/home/az/Projects/PaseoPlugins/yeah-provider`) и не был под контролем версий;
решение владельца — держать его здесь, чтобы правки плагина и правки ядра
жили в одной истории.

Собранный бандл не знает, где он лежит (демон Paseo выполняет его через
`eval`, и `__dirname` в нём не определён), поэтому корень ядра приходит
извне: переменная окружения `YEAH_REPO_PATH`, а иначе — настройка `repoPath`.

## Установка

```sh
paseo plugin install /home/az/Projects/yeah/plugin/yeah-provider
```

Требуется `pluginsEnabled: true` в конфигурации демона (уже так) и живой
`~/.paseo/config.json`. Путь к ядру, модель и профиль разрешений — в
настройках хоста (Paseo → Settings → Yeah).

## Настройки

| Поле | По умолчанию | Смысл |
|---|---|---|
| `repoPath` | `YEAH_REPO_PATH` или `/home/az/Projects/yeah` | корень ядра; `lib/` оттуда грузится |
| `gptelPath` | `""` | каталог сборки gptel; пусто — свежайшая в `~/.emacs.d/elpa` |
| `emacsPath` | `""` | путь к Emacs; пусто — ищется в известных местах |
| `model` | `MiniMax-M3.1-Flash` | модель провайдера |
| `host` | `api.minimax.io` | хост провайдера |
| `profile` | `build` | `build` спрашивает человека, `plan` запрещает правки, `auto` никого не спрашивает (режим без человека) |
| `serviceMode` | `spawn` | размещение ядра: `spawn` — свой Emacs на соединение, `service` — один Emacs на всех агентов, сессии приходят к нему по сокету |
| `serviceName` | `paseo` | имя сервиса: имя его сокета; сервисы с разным именем не мешают друг другу |
| `keyFile` | `~/.config/yeah/live.env` | файл окружения с ключом провайдера |
| `dataHome` | `""` | каталог данных Yeah; пусто — умолчание ядра |

### Ключ провайдера

Ключ **не хранится** в настройках плагина и не попадает в конфигурацию
Paseo. Он лежит в файле окружения вне дерева репозитория (режим `0600`):

```sh
# ~/.config/yeah/live.env
export YEAH_TEST_KEY=...
export YEAH_TEST_HOST=api.minimax.io
export YEAH_TEST_MODEL=MiniMax-M3.1-Flash
```

Плагин читает `YEAH_ACP_KEY` или `YEAH_TEST_KEY` из этого файла (путь
настраивается) и передаёт ключ процессу ACP через окружение. Значение ключа
не печатается и не сохраняется плагином.

Если `YEAH_ACP_KEY` уже есть в окружении демона, файл не читается вовсе.

## Как это работает

1. Плагин регистрирует провайдера `yeah` через `runAcpProvider` — с
   **коннектором**, а не с командой запуска.
2. Коннектор идёт через `yeahTransport` (`server/transport.ts`), и тот
   выбирает размещение: `spawn` — свой Emacs на соединение, `service` —
   общий сервис по сокету. По умолчанию `spawn`, то есть поведение прежнее.
   В режиме `spawn` это Emacs в пакетном режиме с `lib/` ядра и каталогом
   gptel в `load-path`, бэкендом модели через gptel, профилем разрешений и
   `yeah-acp-serve`; в режиме `service` — тот же Emacs, но живой и слушающий
   сокет.
3. Причина — в окружении демона: `ProviderRuntime.resolveLaunch()` собирает
   окружение процесса из настроек демона, и `YEAH_*` до процесса не доходят.
   С коннектором плагин вызывает `spawnProcess` сам и отдаёт демону поток
   провода (`ndJsonStream` из `@agentclientprotocol/sdk`).
4. Всё живое — в окружении (`YEAH_ACP_LIB`, `YEAH_ACP_GPTEL`,
   `YEAH_ACP_MODEL`, `YEAH_ACP_HOST`, `YEAH_ACP_KEY`, `YEAH_ACP_PROFILE`,
   `YEAH_ACP_DATA_HOME`); команда статична, поэтому смена настроек не
   требует пересборки команды и перезапуска плагина.
5. Провод: `initialize` → `session/new` → `session/prompt`. Ответ приходит
   как `session/update`, а вопрос о разрешении — как `session/request_permission`.

### Профиль без человека
Профилей тут два, и их не надо путать: профиль **процесса** и режим **сессии**.
* **Профиль процесса** — настройка `profile` плагина (`YEAH_ACP_PROFILE`).
  Выбирается при старте процесса и наполняет постоянные правила разрешений
  ядра (`lib/yeah-perm.el`): `plan` запрещает инструменты, меняющие мир,
  `build` спрашивает человека, `auto` разрешает всё.  Постоянный **запрет**
  решает всё и на проводе: инструмент, запрещённый постоянно, не спрашивается,
  а получает отказ.
* **Режим сессии** — то, что едет по проводу ACP.  Ядро публикует в ответе
  `session/new` три режима (`plan`, `build`, `auto`; третий приехал с волной
  76), а клиент оркестратора переключает их методом `session/set_mode`.
  Решает именно режим сессии: `plan` запрещает, `auto` разрешает без вопроса,
  `build` спрашивает клиента.
Что из этого следует: прогон без вопросов — это **режим `auto`**, и включается
он на стороне клиента (`paseo run --provider yeah --mode auto`; живой прогон
19 ноября 2026: оркестратор спросил ноль раз).  Настройка `profile` сама по
себе режим сессии не переключает: она наполняет постоянные правила процесса,
а постоянное разрешение вопрос не снимает — снимает его режим сессии.
Что режим **не** делает: он не делает работу агента безопасной.  Удаление
уходит в корзину пользователя, а команды, которые уничтожают на месте,
отвергаются поимённо (`lib/yeah-shell-guard.el`), но границы рабочего
каталога нет и секреты в журнале не маскируются — карта того, что защищено и
что нет, в `docs/AGENT-SAFETY.md`.

### Модель в каталоге провайдера

Ядро по ACP модель не публикует, поэтому `create_agent` с `provider: "yeah"`
отвергался схемой MCP. Модель публикует плагин: трансформер `discover`
добавляет её в каталог провайдера, трансформер `configure` принимает запрос на
эту же модель, а запрос на чужую честно падает.

### Род вызова инструмента

У `tool_call` в ACP есть поле `kind` (род вызова), и ядро его не заполняет.
Род ставит плагин по имени инструмента: `edit`, `read`, `search`,
`execute`. Так интерфейс Paseo показывает вызовы по-разному.

### События очереди

У Yeah есть свои события очереди сессии (`input_queued`, `input_taken`,
`input_recovered`, `input_withdrawn`), и в ACP их нет. Клиент объявляет их в
`_meta` своих возможностей при `initialize` — Paseo не объявляет, и получает
чистый ACP.

### Исход прогона

Исход прогона — тоже словарь ядра: подталкивание, вытолкнувшее модель, прогон,
закончившийся без эффекта, и ошибка, которая его остановила. В ACP такого
метода нет, и клиент, который его не знает, отверг бы обновление целиком.
Поэтому ядро шлёт исход своим уведомлением `yeah/outcome` и только тем, кто его
попросил: объявление `yeah.runOutcome` в `_meta` возможностей клиента.

Объявление добавляет плагин: запрос `initialize` пишет демон оркестратора, и
плагин дополняет его на пути к ядру, не теряя ничего из того, что прислал
демон. Дальше плагин переводит исход в уведомление, которое оркестратор
показывает: `nudge` — «Агент подтолкнут» (`info`), `unfinished` — «Прогон
закончился без результата» (`warning`), `error` — «Прогон упал» (`error`).
Описание уведомления — `payload`, а если его нет — `reason`.

### Расход хода

Счётчик агента в оркестраторе должен показывать токены хода — как у агента
opencode. Ответ на `session/prompt` несёт `usage` (волна 69), но соединение
оркестратора берёт из ответа один `stopReason` и выбрасывает остальное, а
обновление контекста `usage_update` несёт размер окна, а не токены хода.

Поэтому токены едут вторым путём, который принадлежит этому репозиторию: ядро
шлёт их уведомлением `yeah/usage` — методом Yeah, а не ACP — и только тем, кто
попросил их объявлением `yeah.usage` в `_meta` возможностей клиента. Плагин
объявляет этот метод там же, где `yeah.runOutcome`, и переводит уведомление в
событие провайдера `session.usage` — единственное событие, которое оркестратор
переносит в счётчик агента.

Расход собирается из двух частей, и оркестратор обрабатывает их в порядке
своём, поэтому плагин дополняет одну часть другой, а не заменяет: кто бы ни
пришёл последним, в счётчике стоят и токены хода, и размер окна.

### Сервисное размещение

По умолчанию плагин поднимает свой Emacs на каждое соединение: агент пришёл —
Emacs стартовал, агент ушёл — Emacs ушёл. Просто, но дорого: бэкенд модели
настраивается каждый раз, и по stdio запрос, пришедший посреди хода, ждёт
конца хода.

В сервисном размещении Emacs один на всех агентов хоста: он слушает
Unix-сокет, и сессии приходят к нему. Переключение — одна настройка:

* `serviceMode: "service"` — общий сервис;
* `serviceName` — имя сервиса, то есть имя его сокета
  (`yeah-service-<имя>.sock` в `XDG_RUNTIME_DIR/yeah`). Сервисы с разным именем
  не мешают друг другу.

Путь сокета — тот же, что у ядра (`yeah-service-socket-path` в
`lib/yeah-service.el`), поэтому сервис, поднятый из Emacs, и сервис, поднятый
из плагина, не выдают друг друга.

Жизнь сервиса привязана к сокету жизни хозяина (`yeah-life-<тег>-<pid>.sock`):
плагин слушает его и закрывает сервис, когда уходит, — сервис без хозяина ждёт
клиента, который не придёт.

Сервис, который умер, оставляет после себя сокет: файл переживает процесс.
Поэтому плагин не считает файл доказательством жизни — он спрашивает сам
сокет, и мёртвый сокет поднимает сервис заново (волна 74).

**Умолчание прежнее** (`spawn`, свой Emacs на соединение), и это сделано
нарочно: какое размещение канонично и что делать с сервисом после его падения
— вопрос владельца (`docs/PASEO-INTEGRATION-PLAN.md` §5.3).

### Steering

Steering — это сообщение, пришедшее агенту посреди хода и не заменяющее ход.
Оркестратор шлёт его с `delivery: "steer"`, а провайдер должен объявить
возможность `prompt.steer`.

Адаптер ACP библиотеки оркестратора эту возможность не знает: он объявляет
четыре, и запрос с `delivery: "steer"` обрывает текущий ход и начинает новый
— это замена хода, а не steering. Поэтому steering делает плагин:

* объявляет `prompt.steer` в возможностях соединения и в событии
  `session.opened` — но только если оркестратор эту возможность предложил
  (соединение, выбравшее непредложенную возможность, оркестратор вовсе не
  принимает, и старый хост сохраняет свой отказ);
* перехватывает запрос с `delivery: "steer"` и переводит его в `session/steer`
  ядра (`lib/yeah-acp.el`), минуя адаптер;
* отвечает оркестратору тем же идентификатором хода, который идёт
  (`acp:<clientMessageId>`).

Идущий ход при этом не прерывается: ядро не получает `session/cancel`, а
адаптер запрос не видит вовсе.

Два факта для перевода берутся с провода: идентификатор сессии ядра — из
ответа на `session/new`, а какой сессии оркестратора она принадлежит — из
метки `yeah.session`, которую плагин кладёт в параметры открытия сессии
(адаптер переносит её в `_meta` запроса без изменений); идентификатор идущего
хода — из событий адаптера: ход, который начался, и есть ход, который идёт.

**Ограничение.** Над stdio ядро читает следующий запрос только после конца
хода, поэтому уточнение, пришедшее по stdio, читается поздно и становится
обычным вопросом. Своевременным steering делает сервисное размещение (см.
выше): проверка steering'а идёт именно в нём.

Живой прогон через настоящий оркестратор был 19 ноября 2026: уточнение
дошло до модели в идущем ходе, и ход не был ни прерван, ни заменён.  То же
проверяет и проверка волны — кодом плагина против настоящего ядра
(`tests/checks/check-the-plugin-steers-the-running-turn.sh`).

### Кодировка провода

Провод — UTF-8, и байты сообщения уходят как есть: русский ответ агента
приходит в Paseo читаемым. Раньше Emacs читал байты unibyte-строки как
Latin-1 и писал их обратно как UTF-8, и весь не-ASCII текст приходил
кракозябрами (дефект ядра, волна 40).

## Что ограничено по проводу

Это ограничения ядра Yeah, а не плагина; плагин их не обходит и не прячет.

- **Отмена.** По stdio отмена читается только после того, как текущий
  промпт дошёл до конца: кнопка «стоп» в Paseo ждёт конца хода. Сокетный
  транспорт ядра эту границу снимает (`yeah-acp-serve-socket`), и переход на
  него — работа плагина, а не ядра. **С 2026-11-19 переход сделан**:
  настройка `serviceMode` переводит плагина на сокет (см. «Сервисное
  размещение»). Граница снимается сервисным размещением, а не тем, что
  оно теперь по умолчанию: умолчание прежнее — `spawn`, то есть stdio.
- **Профиль и модель не переключаются на лету.** `session/set_mode` и
  `session/set_config_option` ядро не знает: профиль выбирается при старте
  процесса, модель — там же.
- **`mcpServers` — не игнорируются.** Ядро соединяется с серверами, которые
  клиент назвал в `session/new`, и их инструменты становятся инструментами
  ходов этой сессии: волна 66 дала ядру транспорт MCP по HTTP (stdio тоже
  есть).  Что осталось за пределами ядра — кто поднимает эти серверы: Paseo
  передаёт их имена и адреса, а процесс-сервер живёт там, где его подняли
  (вопрос владельца, `docs/PASEO-INTEGRATION-PLAN.md` §5.4).
- **Вызовы инструментов без диффа.** Ядро шлёт в `tool_call` аргументы
  вызова (`rawInput`), а в `tool_call_update` — результат (`rawOutput`), но
  аргументы приходят **позиционным списком значений**, а не именованными
  полями. Paseo читает `filePath`/`oldString`/`newString`, поэтому дифф
  правки в UI Paseo не появляется.
- **Рабочий каталог сессии не применяется к инструментам.** Относительные
  пути агента считаются от рабочего каталога процесса Emacs, а не от `cwd`
  задачи: в живой проверке `bash` агента выполнился в каталоге установки
  CLI Paseo.
- **Журнал — источник истины.** ACP проецирует 11 из 29 типов событий; исход
  прогона (нудж, `unfinished`, ошибка) доезжает до оркестратора через плагин,
  а остальное (дочерние агенты, подробности расхода) — в JSONL по адресу
  `<dataHome>/yeah/projects/<хэш каталога>/sessions/<id>.jsonl`.
