### Где сессия ослабила дисциплину

- **Формулировка о публикации.** «Коммит запушен» не соответствует состоянию
  репозитория: `main` опережает `origin/main` на один коммит. Вывод о
  публикации должен проверяться `git status`, а не утверждаться по факту
  коммита.
- **Документация отстала от кода.** Материал сессии правит README, но
  `AGENTS.md` и `docs/ARCHITECTURE.md` остались с прошлым состоянием (разбор
  ниже).
- **Процесс с субагентами.** Часть параллельных агентов терялась (`agent-7…11`,
  фоновые задачи), и работу возвращали вручную в изолированных ветках. План
  должен резервировать время на ручной возврат, а не считать параллелизм
  гарантированным.
- **Начало реализации до одобрения плана.** В конце сессии обсуждался запуск
  16.1 до ответа человека; в этом разборе порядок сохранён — сначала план.

## 7. Почему проверки идут долго и как их ускорили

Замер на этой машине (2026-11-15, Emacs 30.2 из nix-профиля):

| Фаза | Время |
|---|---|
| `byte-compile-all` (53 файла) | 2.9 с |
| `ert tests/unit/*.el` (358 тестов) | 5.5 с |
| `check tests/checks/*` (53 канарейки) | 58 с |
| `bench` (самопроверка аппарата измерений) | 2.3 с |

Сами проверки быстрые. Время съедала **фаза отрицательных контролей**: mathc
запускает каждую проверку дважды — один раз как есть, второй раз с испорченным
предметом. Пока предмет исправен, всё мгновенно; когда предмет сломан,
канарейка ждёт того, чего не будет, — до конца своего таймаута.

Замер «проверка → проверка с контролем» по всем claim'ам (под нагрузкой общей
машины):

| | время |
|---|---|
| сумма всех проверок | 287 с |
| сумма всех проверок с контролем | 420 с |

Семь claim'ов дают 227 с из этих 420 с — те, где сломанный предмет заставляет
канарейку ждать того, чего не будет:

| claim | проверка | с контролем | накладные |
|---|---|---|---|
| `client-sees-service-death` | 6.7 с | 60.3 с | **+53.6 с** |
| `client-disconnect-cancels-the-run` | 2.8 с | 55.9 с | **+53.1 с** |
| `service-ui-answers-permission` | 1.2 с | 31.3 с | +30.1 с |
| `bridge-live-server` | 1.7 с | 31.6 с | +29.9 с |
| `client-drives-service` | 15.2 с | 38.1 с | +22.9 с |
| `runtime-stays-responsive` | 3.5 с | 26.4 с | +22.8 с |
| `service-lifecycle` | 1.0 с | 16.0 с | +15.0 с |

Что сделано:

- **Ожидания сокращены там, где ответ локальный.** Ответ по сокету приходит за
  миллисекунды, поэтому ожидание в 10–20 секунд было запасом, а не
  требованием: теперь 4–8 секунд (`tests/checks/*`), и таймауты подключения
  6–10 секунд вместо 15–20. Проверка не ослабла — она по-прежнему падает,
  просто падает раньше: `wire-cancel-preempts` под контролем 20.9 с → 8.9 с.
- **`scripts/dev check` печатает время каждой проверки и общий итог** — видно,
  где именно уходит время, без догадок.
- **Сервис ищет тот же Emacs, что и человек** (`yeah-service--emacs-program`):
  раньше он запускался по имени `emacs`, которого на этой машине нет в PATH.
  Это был не только дефект проверок, но и реальная поломка продукта: новый
  путь входа `M-x yeah` не стартовал бы там, где Emacs стоит в профиле.

Чего ускорить нельзя: сама схема mathc — «проверка, потом та же проверка с
испорченным предметом» — это и есть смысл метода, её нельзя пропускать. А
`check-bridge-keeps-the-answer` (≈16 с) медленный по существу: он поднимает
демон Emacs и делает 120 чтений через `emacsclient`, чтобы гонка с потерей
ответа была достоверной; ослаблять его ради секунд нельзя.

Отдельный фактор — сама машина: 7.8 ГБ RAM, 3.9 ГБ в свопе и параллельная
работа других агентов. На такой машине прогоны mathc дважды убивались OOM
(смерть процесса без вердикта — это не «red», это «unknown»). На свободной
машине те же прогоны заметно быстрее; повторный прогон с ретраями даёт
устойчивый результат.

### Итог прогона после ускорений

| | было | стало |
|---|---|---|
| `./scripts/dev run` (74 claim'а, 74 контроля) | 10–20 мин, три убитых прогона | **325 с, exit 0** |
| вердикт карты | `unknown` (3 claim'а `inconclusive`) | **`green`** |
| отрицательных контролей доказано | — | **74 из 74** |

Три `inconclusive`, которые оставались после первой волни работы, оказались не
дефектом проверок, а **устаревшими контролями**: код переехал (отмена — из
`yeah-turn-cancel` в `yeah-control-cancel`, путь ответа — в
`yeah-client--handle`), а `sed` продолжал искать старую строку. Метод отверг их
честно: `control_reach: nothing` — «контроль не достал до предмета» — это не
«red», а «unknown». Контроли переписаны под текущий код и проверены вручную:
каждый ломает проверку с кодом возврата 1. Та же проверка всех 74 контролей
(применение в копии + сравнение дерева) показала: ни один не остаётся
бесполезным.

## 8. Команды проверки

```sh
./scripts/dev byte-compile-all        # чистая компиляция ядра
./scripts/dev ert tests/unit/*.el     # 358 unit-тестов
./scripts/dev check tests/checks/*     # 53 канарейки, с временем каждой
./scripts/dev bench                    # самопроверка аппарата измерений
./scripts/dev map                      # карта: 74 claims, 22 uncovered
./scripts/dev gate                     # run + map, exit 0 = green
```
