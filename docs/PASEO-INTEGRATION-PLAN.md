## 3. Разрывы

### 3.1 `cwd` сессии не применяется к инструментам — P0, ядро (§18.3, п.1)

Цепочка рвётся в одном месте:

```text
session/new {cwd: "/home/az/Projects/yeah"}     lib/yeah-acp.el:467
  → состояние сессии (:cwd)                     lib/yeah-acp.el:448
  → frozen-вход (:cwd)                           lib/yeah-acp.el:187
  → ход (input → :frozen)                       lib/yeah-turn.el:1403
  → ✗ ни один инструмент его не читает
```

Инструменты считают относительные пути от `default-directory` процесса Emacs:
`lib/yeah-files.el:76`, `lib/yeah-process.el:81`, `lib/yeah-git.el:126`. В
плагинном маршруте Paseo `default-directory` — это каталог демона, потому что
процесс ACP поднимается без `cwd` (`plugin/yeah-provider/server/yeah.ts`, `acpStream` →
`spawnProcess` без опции `cwd`), а в конфигурационном маршруте — `cwd`
демона (`packages/server/src/server/agent/providers/acp-agent.ts:1339-1340`,
`cwd: process.cwd()`).

Живое подтверждение (2026-11-16, разбор §2.9.4): модель, веленная записать
файл по относительному пути `answer.txt`, записала его в рабочий каталог
сервиса; в `cwd` сессии файла не было. Измерено дважды.

**Почему это P0.** Это единственный разрыв, из-за которого агент делает не
то, что от него ждут, и не сообщает об этом: путь «прочитал → исправил →
проверил» уводит в другую директорию, и проверка в задаче не проверяет то,
что агент изменил.

**Где чинить.** Связка уже есть: ход несёт frozen-вход (`lib/yeah-turn.el:1403`),
а инструмент выполняется под привязкой сессии (`lib/yeah-turn.el:439`,
`yeah-turn--run-or-refuse`). Значит, привязка `default-directory` к `cwd` из
`(plist-get (plist-get (yeah-turn-input turn) :frozen) :cwd)` в этой точке
закрывает `read`, `write`, `edit`, `bash`, `git_*` разом. Для асинхронных
инструментов (`job`) привязки не будет — там каталог должен уходить в
аргументы задания. Это ровно то, что волна 43 обещает проверить: «инструмент
этой сессии видит временный каталог, а не каталог процесса».

### 3.2 Маршрут ACP в Paseo отказывает в steering'е — P0, Paseo (в плане нет)

Ядро steering умеет: `session/steer` реализован
(`lib/yeah-acp.el:752`, `lib/yeah-acp.el:598`). Маршрут ACP в Paseo его не
использует — соединение отказывает до отправки промпта:

```text
packages/plugin/src/server/acp.test.ts:766
  it("refuses unsupported steering before sending an ACP prompt", ...)
  → rejects.toThrow("prompt.steer")
```

То есть возможность в ядре есть, а оркестратор её не достаёт. Следствие:
follow-up в Paseo для агента Yeah — это `interrupt` (отмена и новый промпт),
а не «подсказать посреди хода». Для агента, который сам пишет код и сам
проверяет, это разница между «подсказать» и «начать заново».

Правка — в репозитории Paseo
(`packages/plugin/src/server/acp-internal/connection.ts`): при
`delivery === "steer"` отправлять `session/steer` клиенту ACP, который его
поддерживает. Это **работа в чужом репозитории**: либо апстрим-PR в Paseo,
либо локальная правка с форком.

### 3.3 Аргументы вызова инструмента — позиционный список — P1, ядро (§18.3, п.4)

Ядро читает напечатанную форму аргументов и кладёт в `rawInput` вектор
значений (`lib/yeah-acp.el:296`, `yeah-acp--tool-input`):

```text
:rawInput ("answer.txt" "42" nil "")            ; write
:rawInput ("pwd && ls -la" 30 "." 5000)         ; bash
```

Paseo читает **именованные** поля и без них не рисует правку
(`packages/plugin/src/server/acp-internal/connection.ts:1337-1341`):

```ts
filePath:  typeof input.filePath  === "string" ? input.filePath  : ...
oldString: typeof input.oldString === "string" ? input.oldString : undefined
newString: typeof input.newString === "string" ? input.newString : undefined
```

Дифф появляется только при `kind === "edit"`; род сейчас ставит плагин по
имени инструмента, а ядро его не шлёт (в этом же пункте плана — claim
`a-tool-call-carries-its-kind`).

**Где чинить.** Имена параметров известны ядру — они объявлены в спецификации
инструмента (`lib/yeah-tools.el`, `yeah-tools-get`). Значит, `rawInput` должен
быть объектом, собранным из имён: `filePath`, `oldString`, `newString` для
`edit`; `path` для `read`/`write`; `command` для `bash`.

### 3.4 Режимы (Plan/Build) не публикуются — P1, ядро + плагин (§18.3, п.2)

Paseo берёт режимы из ответа `session/new`
(`packages/plugin/src/server/acp-internal/connection.ts:473-495`, каталог:
`toProviderCatalog`, строки 1274-1290) и переключает их через
`session/set_mode` (строки 737-747). Ядро отвечает на `session/new` только
`(:sessionId ID)` (`lib/yeah-acp.el:464-471`), а метода `session/set_mode` не
знает — `-32601`.

У профилей разрешений ядра уже есть ровно два нужных режима — `plan` и
`build` (`lib/yeah-perm.el:101`, `lib/yeah-perm.el:105`): `plan` запрещает
мутирующие инструменты, `build` спрашивает человека. Но профиль выбирается
при старте процесса, а не на лету.

**Разделение работы:**

* **Ядро:** уметь менять профиль на лету и публиковать `modes` в ответе
  `session/new` (`currentModeId` + `availableModes`).
* **Плагин:** публиковать режимы в каталоге провайдера
  (`ProviderCatalog.modes`, `packages/plugin/src/server/provider.ts:310`) и
  обрабатывать переключение. Это возможно **без правок Paseo**: трансформеры
  спрашиваются первыми (`connection.ts:729-740`), и трансформер `configure`
  может вернуть `"handled"`, не спрашивая ядро вовсе. Ответ плагина обязан
  подтвердить новое состояние через `notification`-трансформер с
  `{type: "config", config}` (`connection.ts:1021`).

### 3.5 Модель не входит в конфигурацию сессии — P1, ядро (§18.3, п.3)

Ядро не публикует `configOptions` и не знает `session/set_config_option`.
Модель — одна на процесс, и приходит окружением при старте. Плагин закрывает
это фикцией: `yeahCatalog` добавляет модель в каталог, `yeahConfigure`
принимает запрос на **ту же** модель и пропускает чужую
(`plugin/yeah-provider/server/catalog.ts`). То есть в UI Paseo модель видна и выбирается, но
переключение на другую честно падает.

Смена модели на лету в ядре технически возможна: `gptel-model` — переменная,
и транспорт `yeah-gptel-request` берёт её на каждом запросе.

### 3.6 `session/close` не реализован — P1, ядро (§18.2)

`session/close` среди девяти методов диспетчера нет (§2). Paseo вызывает его
при закрытии сессии агента
(`packages/plugin/src/server/acp-internal/connection.ts:690-698`), и ошибка
глотается (`.catch(() => undefined)`) — то есть тихо. Следствия: сессия Yeah
остаётся открытой, процесс Emacs переживает агента. План владельца §18.2
называет это своей первой частью: «сервер должен иметь способ закончиться, не
зависящий от того, что клиент закрыл трубу», и говорит, что плагин закрывает
трубу, а «сторона ядра даёт ему способ сказать об этом». Именно этим
способом и будет `session/close` (или его равнозначная семантика).

### 3.7 `mcpServers` игнорируются — P2, ядро (§18.3, п.5)

Paseo подставляет свои MCP-серверы в `session/new`
(`connection.ts:463`, `toAcpMcpServers`), ядро их принимает и не использует.
Практическое следствие: инструменты оркестратора (создать агента, послать
агенту сообщение) в руках агента Yeah не появляются — у него только его
собственные инструменты (20 в текущей сборке: `yeah-tools-names`, проверено
запуском 2026-11-18).

### 3.8 Исход прогона не виден оркестратору — P2, ядро (в плане нет)

По проводу идут 8 видов событий (`lib/yeah-acp.el:358`); `usage`, `nudge`,
`unfinished`, `error` и записи о дочерних агентах — нет. Оркестратор видит
`stopReason` и текст агента, но не видит: сколько токенов ушло, что модель
дважды описала намерение вместо действия, что прогон кончился без эффекта.
Источник истины — JSONL-журнал, но читать его оркестратор не умеет.

Механизм расширения уже есть и работает: события очереди едут только тем
клиентам, которые объявили их в `_meta` (`lib/yeah-acp.el`,
`yeah-acp--queue-events-p`). Тот же приём годится для `usage`/`nudge`/
`unfinished`, а плагин может переводить их в vendor-обновления через
`notification`-трансформер (`AcpVendorUpdate`,
`packages/plugin/src/server/acp.ts`).

### 3.9 Плагин поднимает свой Emacs на каждое соединение — P2, плагин (в плане нет)

Сейчас коннектор плагина сам вызывает `spawnProcess` и поднимает Emacs в
пакетном режиме на каждое соединение (`plugin/yeah-provider/server/yeah.ts`, `acpStream`). Это
расходится с решением `docs/ARCHITECTURE.md` §7: **основное развёртывание —
сервисное**, и «провод — stdio или локальный сокет; на сокете соединение
является процессом, цикл событий живёт, и отмена обрабатывается, пока промпт
ещё идёт — stdio этого не может».

Сервисная часть в ядре уже есть и работает: `yeah-service-start` поднимает
`yeah-acp-serve-socket` (`lib/yeah-service.el:133`, `lib/yeah-acp.el:825`), а
`yeah-service-connect` подключается к нему (`lib/yeah-service.el:193`).

Что это даёт:

* отмена вытесняет идущий промпт (а на stdio — нет: `lib/yeah-acp.el:798`,
  докстринг `yeah-acp-serve`);
* один Emacs вместо одного на соединение;
* бэкенд модели и gptel настраиваются один раз, а не на каждый процесс;
* уходит часть открытого дефекта: после живых прогонов остаются процессы
  Emacs, один из них крутится в плотном цикле userspace (`docs/PLAN.md`
  §17.1; разбор §2.10.5) — локализовать spin не удалось, и он стоит на пути
  живого запроса к провайдеру;
* клиент закрывает соединение — процесс уходит (в плагине закрытие stdin уже
  сделано: `endInput`).

Цена: коннектору плагина нужен клиент сокета вместо `ndJsonStream` поверх
stdio. SDK `@agentclientprotocol/sdk` работает с любым дуплексным потоком,
поэтому это переход на `net.connect` с адаптером в `ReadableStream`/
`WritableStream`.

**Связь с волной 42.** Волна 42 говорит: плагин закрывает трубу сервера,
когда сессия агента кончена. На сокете «трубы» нет — там закрывается
соединение, и завершение жизни процесса Emacs становится делом сервиса, а не
плагина. То есть P4 (§4.2) меняет и волну 42, и то, как измеряется её
второй критерий («живая проверка плагина не оставляет процессов»).

### 3.10 «Мусорные» сессии при каждом discovery — P2 (в плане нет)

`discover()` в маршруте ACP создаёт **настоящую сессию** ради списка
моделей (`connection.ts:523-528`):

```ts
const response = await this.call(this.connection.newSession({ cwd, mcpServers: [] }));
```

Каждое подключение к провайдеру оставляет в журнале Yeah сессию, которая
ничего не делала. Мелочь, но она делает журнал нечитаемым именно там, где он
и нужен — в расследовании прогонов. Чинится либо ядром (проба не создаёт
сессию), либо плагином (сессия помечается как проба и закрывается).

### 3.11 Профиль без человека — вопрос владельца

В маршруте ACP каждый вопрос о разрешении доходит до человека, а `build`
спрашивает по каждому мутирующему вызову (`lib/yeah-perm.el:105-118`).
Оркестратор, который запускает агента без участия человека, на этом упирается.
Решение — не в коде (см. §5).

  лежит осиротевший журнал от прогона с относительным путём данных. В новом

* **Плагин под контролем версий — сделано 2026-11-18.** По решению владельца

## 4. План

### 4.1 Что уже есть в плане владельца (§18)

Разбор подтверждает список волны 43 по коду: он совпадает с §3.1, §3.3, §3.4,
§3.5 и §3.7 — один в один, включая порядок.

**Волна 42 — сервер не переживает агента и не крутится** (§18.2). Claim'ы:
`the-server-exits-when-the-session-is-over`,
`the-server-does-not-spin-when-the-provider-is-silent`. Покрывает §3.6
(жизнь сервера) и часть §3.9 (процессы на соединение) — см. оговорку в §3.9.

**Волна 43 — поверхность ACP, нужная оркестратору** (§18.3). Claim'ы:
`a-session-runs-in-its-own-directory`, `a-tool-call-carries-its-kind`,
`a-tool-call-carries-named-arguments`,
`a-session-changes-its-permission-profile-over-the-wire`,
`a-session-changes-its-model-over-the-wire`,
`the-mcp-servers-of-a-session-reach-the-model`. Порядок: сначала `cwd`,
затем род и именованные аргументы, затем `session/set_mode`, затем модель,
затем `mcpServers`.

**Что разбор добавляет к волне 43** (не отменяя её):

1. **Род вызова (`kind`) — не только в плагине.** Сейчас род ставит трансформер
   плагина по имени инструмента (`plugin/yeah-provider/server/yeah.ts`, `TOOL_KINDS`). Ядро должно
   слать его само: `kind` — поле ACP, и клиент, который проверяет провод,
   вправе ждать его от агента. Плагин тогда оставляет трансформер как
   запасной путь, а не как основной.
2. **Имена аргументов — по спецификации инструмента, а не по догадке.**
   Словарь имён (`filePath`, `oldString`, `newString`, `path`, `command`) должен
   жить в ядре рядом со спецификацией инструмента, иначе плагин и ядро
   разойдутся в именах.
3. **`session/close` — в волну 42, а не в 43.** Это завершение жизни сервера,
   то есть предмет волны 42, и §18.2 уже говорит, что «сторона ядра даёт
   плагину способ сказать об этом».

### 4.2 Чего в плане нет — четыре предложения

Номера волн назначает владелец; серия уже занята (51, 52 названы в §17.3,
53 — в работе другой сессии).

**P-A. Steering в маршруте ACP (Paseo).** §3.2. Правка в чужом репозитории:
`packages/plugin/src/server/acp-internal/connection.ts` отправляет
`session/steer`, когда `delivery === "steer"`. Claim: маршрут ACP умеет
перенаправить идущий ход. Проверка: тест маршрута в Paseo — промпт в полёте
плюс `prompt.steer` → `session/steer` уходит агенту. Контроль: убрать
отправку → тест падает.

**P-B. Исход прогона на проводе (ядро + плагин).** §3.8. Claim: провод
говорит оркестратору, что прогон сделал и чем кончился. `usage`, `nudge`,
`unfinished` и `error` проецируются за тем же расширением, что и события
очереди (`_meta` при `initialize`); плагин переводит их в vendor-обновления
через `notification`-трансформер. Проверка: разговор с настоящим
ACP-сервером, в котором прогон остаётся без эффекта, — клиент получает
`unfinished`. Контроль: убрать проекцию `unfinished` → проверка падает.

**P-C. Проба каталога не оставляет сессии (ядро или плагин).** §3.10. Claim:
подключение к провайдеру не оставляет в журнале сессии, которая ничего не
делала. Проверка: подключение к каталогу, затем — ни одной записи о пробной
сессии в журнале. Контроль: вернуть создание сессии на пробу → проверка
падает.

**P-D. Плагин говорит с сервисом по сокету (плагин).** §3.9. Claim: плагин
подключается к сервису Yeah по Unix-сокету и не поднимает свой Emacs на
соединение. Что это меняет: отмена вытесняет идущий промпт; Emacs один, а не
по одному на соединение; бэкенд модели настраивается один раз; критерий
«живая проверка плагина не оставляет процессов» волны 42 меняется на «сервис
живёт, а соединение закрывается». Проверка: офлайн-тест плагина с живым
сервисом — `initialize`, `session/new`, `session/prompt`, и отмена во время
промпта вытесняет его. Контроль: вернуть подъём Emacs на соединение →
проверка отмены падает.

## 5. Решения владельца

Ни одно из этих не решает агент (`docs/PLAN.md` §17.2, §18.5).

1. **Профиль без человека.** Нужен ли профиль, который разрешает
   мутирующие вызовы без вопроса (для оркестратора, работающего без
   человека), и кто отвечает за его границы? Это вопрос доверия, а не кода.
2. **Steering: апстрим Paseo или форк.** P-A — правка в чужом репозитории.
   Форк означает своё сопровождение.
3. **Сервисное размещение против пакетного Emacs.** P-D переводит плагина на
   сервис: один долгоживущий Emacs вместо процесса на соединение. Это меняет
   эксплуатационную модель (кто поднимает сервис, где его журнал, что
   происходит после его падения) — и меняет критерий волны 42.
4. **Место Yeah в иерархии агентов Paseo.** Сейчас Yeah — провайдер среди
   прочих. Нужно ли, чтобы агент Yeah мог вызывать других агентов Paseo
   (`create_agent`, `send_agent_prompt`)? Это упирается в §3.7: `mcpServers`
   игнорируются, и инструментов оркестратора у агента нет.
5. **Волны 42–43 против добавленных P-A…P-D.** План владельца (§18) уже
   назначен; добавленные пункты в него не входят. Вмешательство в этот
   порядок — решение владельца.
