# Диаграммы для сайта Yeah — разбор, инструмент и расстановка

> **Статус документа:** предложение и разбор, а не задача. Ни одна диаграмма на
> сайте пока не нарисована. Документ отвечает на три вопроса: какие
> диаграммы нужны, чем их рисовать и что должно произойти в коде, чтобы
> диаграммы не расходились с системой.
> Дата разбора: 2026-11-20. Источники — код (`lib/`, `plugin/`, `site/`),
> `docs/ARCHITECTURE.md`, `docs/PLAN.md`, `spec.json`, `waves/`.
>
> **Исправление к первой версии этого документа.** Первая редакция предлагала
> «привести документацию в соответствие с кодом». Это неверно:
> `docs/ARCHITECTURE.md` объявляет себя нормативной целью, а не описанием
> сегодняшнего состояния. Правильная постановка — обратная: **код отстаёт от
> архитектуры, и работать над этим должен код.** Разбор ниже пересобран на
> этом принципе; §11 и `docs/ARCHITECTURE-CATCHUP-PLAN.md` — его следствие.

## 1. Зачем документ

Задача: на сайте Yeah вместо одной ASCII-картинки в разделе `*architecture*`
должен быть набор **классических UML-диаграмм**, раскрытых по тексту, а не
собранных в галерею. Форма — классическая UML-нотация, цвет — палитра сайта
(лицо Emacs 30.2 в светлой теме, modus-vivendi в тёмной). Инструмент рисования
должен быть специализированной библиотекой, а не ручной отрисовкой SVG.

Цель, которую диаграммы обслуживают: человек, открывший сайт, должен за
первые два экрана понять **что это, как работает цикл, где оно живёт и с кем
говорит**.

## 2. Что за проект (краткая карта)

Yeah — «Yeah, Emacs Agent Harness». Ядро — Emacs Lisp, 65 модулей в `lib/`,
около 17 000 строк. Наружу ядро говорит тремя способами: ACP (агентный
протокол), MCP (протокол инструментов) и мост `emacsclient` к живым буферам
человека. Модель достигается через приватный адаптер gptel; оркестратор Paseo
подключается плагином `plugin/yeah-provider/` (TypeScript), который поднимает
Emacs и говорит с ним по ACP.

Три «размещения» — `attached`, `service` (основное), `batch` — пишут одни и
те же события в один и тот же журнал.

Ключевое для диаграмм: журнал (`lib/yeah-session.el`) — источник истины, всё
остальное — проекции журнала. Это единственная мысль, которую сайт обязан
донести.

mode line.

Единственная диаграмма сейчас — `<figure class="ascii-figure">` в
`site/index.html:482–506`: 23 строки ASCII, рисующие слои (драйверы → Session
API / Run Controller → адаптер модели / реестр инструментов / политика →
планировщик → журнал → проекции → размещения). Она честная по содержанию, но

Следствие, важное для плана: **ни одна новая секция не нужна.** Все диаграммы
размещаются внутри существующих двенадцати окон — значит, таб-бар, меню
Buffers и отображение скролл-спая (`site/script.js:195`) остаются нетронутыми.
Это и правильнее: кадр Emacs не должен обрастать лишними буферами.

## 4. Документ и код: кто отстаёт

Это главное, что пришлось пересмотреть.

`docs/ARCHITECTURE.md` открывается словами: «**Document status: normative
target.** This file describes the system Yeah is being built to become. It is
not evidence that the system already works.» И дальше: «When this document and
the code disagree, the disagreement is a finding. Do not silently rewrite either
side.»

Отсюда порядок по умолчанию:

1. **Документ — цель.** Код — путь к ней.
2. **Расхождение — находка, а не повод смягчить документ.** Документ
   переписывают только тогда, когда он действительно неточен, и это решение
   владельца (`docs/PLAN.md` §17.2), а не молчаливая правка агента.
3. **Сайт — описание настоящего.** Сайт states the product at the level its
   evidence supports (`site/README.md:158–164`); нормативная цель живёт по
   ссылке на `ARCHITECTURE.md`. Поэтому рисунок на сайте показывает то, что
   работает сегодня, а целевое состояние — предмет плана работ, а не рисунка.

Практический смысл для этого документа: находки из §11 — это **не «поправить
документ»**. Это волны в коде. Схемы на сайте появятся после того, как
зафиксировано, что именно они показывают; часть схем (машина состояний)
должна быть **порождена кодом**, чтобы не расходиться с ним.

## 5. Инструмент: PlantUML

Рукописный SVG отвергнут: «специальная библиотека» для UML — это PlantUML.
Проверено на практике, на этой машине, сегодня.

### 5.1 Что установлено и как запускается

На хосте не было ни Java, ни Graphviz, ни PlantUML. Установлено через nix
(`sudo nix-env -iA nixos.plantuml`): **PlantUML 1.2025.10, Graphviz 12.2.1,
OpenJDK 21.0.10**. Профиль nix-env на этом хосте поставить не смог (ошибка
«creating a garbage collector root … is forbidden»), но все пакеты скачались в
стор, и бинарники работают:

```sh
PLANTUML=/nix/store/6px1l8dw53rwl49yn0znr5sd7i3nvrfh-plantuml-1.2025.10/bin/plantuml
$PLANTUML -version
```

**Перепроверено 20 ноября 2026.**  Собранных выходов в сторе на этот день не
было: остались только деривации (`.drv`), а сам `plantuml`, `java` и `dot` не
находились ни в `PATH`, ни в nix-профиле — то есть утверждение «бинарники
работают» было верно в момент записи и перестало быть верным, когда стор
почистили.  В тот же день выходы пересобраны (`nix profile install
nixpkgs#plantuml`, версии совпали с записанными выше: PlantUML 1.2025.10,
Graphviz 12.2.1, OpenJDK 21.0.10+7), путь выше снова существует, `plantuml
-testdot` находит Graphviz, а SVG одного и того же файла, отрендеренный дважды
в разные каталоги, совпал **побайтово**.  Вывод для репозитория прежний и
теперь измерен: скрипт обязан искать инструмент сам и обязан отвечать кодом
3 («инструмента нет»), когда найти нечего.

Для репозитория это значит, что скрипт обязан искать инструмент сам.  Цепочка
поиска живёт в одном месте — `scripts/lib/tools.sh`, функция `find_tool`, — и
одинакова для всех инструментов: переменная окружения → `PATH` →
`~/.nix-profile/bin` → стор nix (`$NIX_STORE_DIR`, по умолчанию
`/nix/store`).  Готовый путь вшивать в скрипт нельзя: стор-путь
host-specific.

Шаг со стором есть только у PlantUML: `find_plantuml` ищет
`${NIX_STORE_DIR:-/nix/store}/*plantuml*/bin/plantuml`.  У Emacs шага со
стором нет — в сторе лежит много версий Emacs, и выбор версии не должен быть
случайным; `find_emacs` ищет в трёх первых шагах.  Это измерено 20 ноября
2026 (волна 81): обе цепочки живут в одной функции, а различаются только
шагом, который им задаёт вызывающий.

PlantUML — инструмент **автора**, а не рантайма сайта. На публикацию он не
влияет: на GitHub Pages уезжают готовые SVG, как сегодня уезжают `og.svg` и
`logo.svg`.

### 5.2 Что проверено на прототипах

| Свойство | Результат |
|---|---|
| Все четыре нужных типа диаграмм | state, activity, component (с пакетами), deployment — все выражаются и отрисованы |
| Детерминированность | два рендера одного файла дали **побайтово одинаковый** SVG → проверка «диаграмма актуальна» может сравнивать байты |
| Скорость | ~1 с на диаграмму (plantuml + graphviz) |
| Семантика в SVG | `data-diagram-type="STATE"`, у состояний `id="idle"`, у компонентов `id="entity_human"` и `data-entity="human"`, у каждого элемента `data-source-line` |
| Палитра | цвета — инлайновые атрибуты: `#FFFFFF #F2F2F2 #999999 #333333 #000000` — ровно пять токенов сайта, соответствие один-в-один (§6) |
| Тёмная тема | `--dark-mode` PlantUML использует **свою** палитру (`#000000 #333333 #DDDDDD`), не modus-vivendi → тёмный вариант рисуется собственной шкуркой |

Два синтаксических подводных камня, найденных при отрисовке:

* блок `skinparam` требует **одно свойство в строке**; несколько свойств в
  одной строке дают «Some diagram description contains errors»;
* `node` по умолчанию рисуется объёмным кубом — для плоского стиля сайта
  нужен `skinparam nodeStyle rectangle`.

## 6. Палитра: карта «цвет → токен»

Сайт уже держит палитру в CSS-переменных (`site/styles.css:20–140`): `--face-*`
для лиц Emacs 30.2 и `--fl-*` для font-lock, в светлой теме и в modus-vivendi.
Пять цветов, которые PlantUML рисует по умолчанию, попадают в эту палитру
один-в-один:

| Hex в SVG | Токен сайта | Роль |
|---|---|---|
| `#FFFFFF` | `--face-default-bg` | фон узла (буфер) |
| `#F2F2F2` | `--face-fringe-bg` | фон пакета (fringe) |
| `#999999` | `--face-divider` | обводка узла |
| `#333333` | `--face-prose` | стрелки и подписи |
| `#000000` | `--face-default-fg` | текст |

Акценты — по шкале font-lock: `--fl-keyword` (стереотип), `--fl-builtin`
(имя инструмента), `--fl-type` (имя состояния), `--face-error` (запрет),
`--face-success` (разрешённый путь).

Правило, обязательное для всех схем: **цвет никогда не единственный носитель
смысла.** Пунктир, штриховка, подпись «(недостижимо)» дублируют любой цвет —
сайт уже требует этого для статусов (`site/README.md:140`).

Подписи — фиксированная ширина (`--font-mono`), как код и ярлыки в Emacs;
поясняющий текст — `--font-proportional`. То же правило, что в
`docs/SITE-DESIGN.md` § «Two typographic families».

## 7. Пайплайн: от `.puml` до страницы

### 7.1 Состав

```
site/diagrams/*.puml              исходник диаграммы (текст, ревьюится и сравнивается)
site/diagrams/palette-light.puml  шкурка светлой темы (лица Emacs 30.2)
site/diagrams/palette-dark.puml   шкурка тёмной темы (modus-vivendi)
site/assets/diagrams/*.svg        готовые картинки, по две на диаграмму (светлая/тёмная)
scripts/dev diagrams               рендер: .puml → .svg, обе темы
```

**Имена файлов — правило, а не список.**  Исходник `site/diagrams/<имя>.puml`
даёт две картинки: `site/assets/diagrams/<имя>-light.svg` и
`site/assets/diagrams/<имя>-dark.svg`.  Файлы `palette-*` шкурками считаются,
диаграммами — нет: пайплайн их не рисует.

**Состояние на 20 ноября 2026 (волна 81).**  Пайплайн есть и проверяется
проверкой `tests/checks/check-the-diagram-pipeline-renders-both-themes.sh`
(claim `the-diagram-pipeline-renders-both-themes`): подкоманда находит PlantUML
сама, отвечает кодом 3, когда инструмента нет, и кладёт по две картинки на
схему.  Схем пока нет ни одной — первая приходит в волне D1 (машина состояний,
порождённая кодом), остальные — в D2.  Каталог картинок `site/assets/diagrams/`
в репозитории есть (пока в нём только `.gitkeep`: картинок ещё нет, и пустой
каталог git не хранит), и первая картинка его наполнит.  Проверка рисует
прокладную схему в отдельном временном дереве, поэтому пайплайн измерен, а
дерево репозитория проверка не трогает.

* **Формат на сайте — `<img>` плюс переключение темой через CSS.** SVG,
  загруженный через `<img>`, не наследует переменные CSS страницы: `var()`
  внутри внешнего SVG не разрешится, а `<object>` требует отдельного документа
  на каждую тему и плохо работает с `file://`. Поэтому на каждую диаграмму
  приходится два рендера — светлый и тёмный — а CSS переключает, какой из
  них виден. Обе картинки весят 10–20 КБ каждая, переключение мгновенное.
* **Исходник `.puml` и картинка не могут разойтись:** `./scripts/dev diagrams`
  перерисовывает и сравнивает с проверяемым (`cmp`), а проверка
  `check-site-diagrams-current.sh` (в `tests/checks/`) делает то же самое и падает,
  если SVG устарел. Контроль проверки: изменить `.puml` и не перерисовать —
  проверка обязана укусить.
* **Проверка «диаграмма актуальна» — это claim.** Она регистрируется в
  `spec.json` как факт, а волна — в `waves/` как в остальных случаях. Ровно
  так же устроен остальной проект.

### 7.2 Почему не инлайновый SVG

Инлайновый SVG в `index.html` дал бы одну копию на обе темы (через `var()`) и
точное совпадение шрифта с страницей. Но он требует, чтобы SVG жил в HTML, а
HTML тогда перестаёт быть hand-written (нужен генератор, который переписывает
файл) — а это уже build step, которого у сайта нет и который
`site/README.md:3–5` объявляет как отсутствующее. Разница в шрифте (SVG в
`<img>` берёт системный моноширинный шрифт вместо шрифта страницы) —
приемлемая цена за сохранение свойства «без сборки». Если проверка покажет,
что системного шрифта не хватает, альтернатива — инлайн с генератором; это
решение принимается по факту, а не заранее.

### 7.3 Схема машины состояний порождается кодом

Это отдельная и самая важная деталь пайплайна. Машина состояний ядра — не
рисунок художника, а таблица в коде: `yeah-state-list` (11 состояний) и
`yeah-loop--raw-transitions` (31 ячейка). Она читается из живого Emacs:

```sh
$ emacs -Q --batch -L lib --eval '(progn (require (quote yeah-loop))
  (dolist (c yeah-loop-transitions) (princ (format "%s --%s--> %s\n" (nth 0 c) (nth 1 c) (nthcdr 2 c)))))'
idle --user-prompt--> deciding
deciding --stream-end--> post-decide
…
```

Значит, `./scripts/dev diagrams` может **сгенерировать** `.puml` машины
состояний из таблицы, а не рисовать её руками. Тогда диаграмма не может
разойтись с кодом по построению: изменилась таблица — перерисовалась
схема. Для D1–D4 и D6–D8 исходник пишется рукой, но с ссылками
`file:line`, и отдельная проверка следит, чтобы названные модули и строки
существовали.

### D1. Один ход агента — activity, `*readme*`

Заголовок раздела — «Inspect the whole loop», и это буквально просьба о цикле.
Сейчас в разделе три карточки-инварианта и ничего, что показывает движение.

Прототип отрисован и проверен: activity-нотация PlantUML даёт начальный узел,
действия со скруглёнными углами, ромбы решений с подписями «да/нет» и
двойной круг конечного состояния — то есть ровно классическая UML.

Смысловая нагрузка: читатель видит, что модель **предлагает**, а решает
реестр и политика; что журнал — единственное место, где живёт история; что
вызов инструмента может уйти к человеку за разрешением.

### D2. Слои ядра — component diagram, `*architecture*`

Заменяет ASCII-рисунок. Та же картина, но в нотации компонентов, с
пакетами-«драйверы / ядро / проекции» и именами файлов под названиями
блоков. Прототип отрисован: он выглядит ровно в стиле сайта — плоские
заливки, волосяные линии, моноширинный текст.

### D3. Emacs-слой — component diagram, `*why-emacs*`

Сейчас раздел состоит из шести пунктов (BUFFERS, INTROSPECT, EDIT,
DIAGNOSE, COMPOSE, RECOVER) без единой картинки — это самое «текстовое» место
на сайте, и оно идеально для схемы «человек ↔ Emacs ↔ агент». Мост —
единственный путь к живому состоянию, и он **явно одобряемый**: это опорная
мысль раздела, её стоит подписать на самой стрелке.

### D4. Размещения и протоколы — deployment diagram, `*install*`

отмена не может прервать выполняющийся промпт — нужен сокет.

### D5. Состояния прогона — state machine, `*architecture*`

У ядра ровно 11 состояний и 31 ячейка переходов — готовая машина состояний
UML, причём единственная в проекте, которую можно построить, а не
придумать. Источник — код (§7.3).

**Что показывать — вопрос к владельцу, и он не терминологический.** 19 ноября
2026 ячейки `permission-ask`, `ask-user`, `interrupt`, `timeout`, `answer`,
`rate-relief` рантайм не проходил никогда (§11, находка A), и потому стоял
выбор из двух честных вариантов:

* **(а) схема показывает объявленную таблицу** — она полна и красива, но
  показывает машину, которой нет;
* **(б) схема показывает достижимый путь** — она правдива, но на ней
  пропадает то место, где человек ждёт ответа.

**Выбор снят волнами 77 и 80 (20 ноября 2026).**  Состояния ожидания вошли в
машину, а код измерен: у каждой из 31 ячейки таблицы есть живое место тика,
страж которого допускает её состояние `FROM` (измерено вручную, 0 ячеек без
такого места).  Таблица и есть машина, и схема может показывать её целиком.
Оговорка остаётся: **проверка** пока этого не доказывает — она читает метку
места тика, но не связывает место с состоянием `FROM` ячейки (волна 82 чинит
чтение; §11, находка A).  Доказательство статическое и вообще говорит о коде,
а не о том, что каждый прогон проходит каждую ячейку: прогон, который не
встретил занятого провайдера, не берёт `rate-blocked`.  За владельцем остаётся
решение, какую подпись дать схеме.

## 11. Расхождения: код отстаёт от архитектуры

Это находки, а не правки документации. По §4 каждая из них — волна в коде;
подробный план — в `docs/ARCHITECTURE-CATCHUP-PLAN.md`.

### A. Восемь ячеек машины состояний ядро никогда не проходит — **закрыто 20 ноября 2026 (волны 77 и 80)**

Находка была поставлена по коду 12–19 ноября 2026: `lib/yeah-loop.el:20–45`
объявлял 20 переходов, а рантайм вызывал `yeah-turn--tick` только с десятью
метками: `user-prompt`, `stream-end`, `tool-call`, `no-tool-calls`, `continue`,
`tool-end`, `budget-ok`, `budget-overflow`, `compact-done`, `error`
(`lib/yeah-turn.el:304, 610–611, 662–664, 684–685, 717, 844–846, 902, 1005,
1027, 1347`). Метки `permission-ask`, `ask-user`, `interrupt`, `timeout`,
`answer`, `rate-relief`, `tick-resume` не вызывались нигде в `lib/`.

История говорила, что это не «цель, которую не сделали», а **оставшийся
артефакт старого решения**: состояния `awaiting-user-permission`,
`awaiting-user-input`, `blocked-on-rate` введены 12 октября 2026 года
(`5e11402`, `8dc5212`, ветка tier0), а волна 16.1 от 15 ноября (`fda466a`)
заменила блокирующий вопрос на отложенное разрешение (`yeah-approval-async`,
`yeah-approval-resolve`) — и **не тронула** ни `yeah-state.el`, ни
`yeah-loop.el`. Архитектура (D7 «The human is an asynchronous master») описывает
именно асинхронное решение, и код ему соответствовал; отстала таблица
состояний.

**Вердикт был: код.**  Решение владельца от 20 ноября 2026 — вариант
«входят» (A1), и волна 77 ввела состояния ожидания в машину.  Следствия:
состояний стало 11, ячеек — 31, мёртвые ячейки `tick-resume` и `ask-user`
убраны, живые остались в таблице (`docs/PLAN.md` §16.66).

**Закрыта находка волной 80 (20 ноября 2026).**  Проверка
`tests/checks/check-every-transition-of-the-table-is-taken.el` (claim
`every-transition-of-the-table-is-taken`) говорит не про метку, а про ячейку:
машина делает каждую ячейку таблицы, рантайм берёт каждую метку в живом месте
кода, каждая ячейка проходится, и каждое состояние достижимо из первого.
Измерение: 31 ячейка, 17 меток, 11 состояний, 23 места тика — все живые.

**Оговорка, которую нашёл дискриминатор волны 81 (20 ноября 2026).**  Проверка
читает **метку** места тика, но не связывает это место с состоянием `FROM` ячейки:
ветви чтения состояния в проверке были мертвы (`(cdr (cdr form))` вместо
`(cdr form)`), и потому ни одна ячейка не требовала места, которое берёт ход
**из её состояния**.  Код при этом честен — измерено вручную с исправленным
чтением: у всех 31 ячейки есть живое место, страж которого допускает её `FROM`
(0 ячеек без такого места).  Не доказан, а сломан был **вывод**: мутация, при
которой рантайм берёт `stream-end` из `post-decide`, оставляла проверку
зелёной.  Волна 82 чинит чтение и связь; до неё claim'а
`every-transition-of-the-table-is-taken` обещает больше, чем доказывает, и
опираться на него как на доказательство нельзя.

### B. У описания инструмента нет полей, которые требует ARCHITECTURE.md

`docs/ARCHITECTURE.md:535–548` перечисляет «risk/capability classification»,
«shared/exclusive or resource-lock declaration», «timeout and output limits».
В коде спецификация инструмента — это `:name`, `:description`, `:input`,
`:handler` плюс необязательные `:kind`, `:concurrency`, `:async`
(`lib/yeah-tools.el:120–153`). Поля риска, блокировки ресурса, таймаута и
лимита вывода нет; риск выводится из `:kind` и из глобального списка
`yeah-perm--mutating-tools` (`lib/yeah-perm.el:96–97`), лимит вывода — общий
(`lib/yeah-result.el:23`), таймауты — в аргументах инструментов.

**Вердикт: код.** Список меняющих мир инструментов — константа в модуле
прав; инструмент, зарегистрированный в рантайме, не может объявить, что он
меняет мир (при том что claim `registry-async-isolation` требует, чтобы
регистрация в рантайме работала). Это расхождение между архитектурой и
реализацией, а не неточность документа.

**Уточнено 21 ноября 2026 (волна 98):** расхождение закрыто.  В
спецификации инструмента теперь есть поле `:risk` (`lib/yeah-tools.el`),
словарь риска — четыре вида (`read`, `write`, `execute`, `destroy`) — живёт
в новом модуле `lib/yeah-risk.el`, а список меняющих мир перестал быть
константой: `yeah-perm--mutating-tools` стал **функцией**, которая спрашивает
по объявлениям инструментов, и множество «меняющих мир» **измеряется** по
обработчикам (`tests/checks/check-a-tool-declares-its-own-risk.el`), а не
перечисляется.  Перечень безопасных чтений прикреплённого пути
(`lib/yeah-approval.el:74-94`) остался списком имён — это следующий шаг B1
(docs/PLAN.md §16.90).

**Закрыто 22 ноября 2026 (волны 98, `wave-b2`, `wave-b3`):**  контракт
инструмента догнал архитектуру целиком, а не только риском.  `:resource`
(непустая строка) — это блокировка: два вызова, объявившие один ресурс, не
идут одновременно, и инструмент, который только читает, не объявляет
ничего.  `:timeout` (секунды) и `:output-limit` (символы) — границы, которые
модель не может поднять: действует меньшая из объявленной и общей
(`yeah-result-output-limit`), и общая граница есть потолок, который объявление
не поднимает.  Словарь вида остаётся тем, что он есть, — десять видов, и вид
вне словаря отвергается по имени.  **Текст `docs/ARCHITECTURE.md` §5 приведён
к этому коду волной E3** (2026-11-22).

### B′. Внутри самого `yeah-tools.el` docstring разошёлся с кодом

Комментарий `:120–124` перечислял пять видов (`read, edit, search, execute,

think fetch switch_mode other`): код прав, комментарий устарел.

`introspect` (`yeah-result-from-output`, третий аргумент, `lib/yeah-result.el:86`),
а сам инструмент объявляет `:kind "search"` (`lib/yeah-emacs.el:193`); ни один
инструмент `lib/` не объявляет вид вне словаря.  Настоящий дефект — тишина:

**Вердикт: код.** Правка комментария — одна строка; неизвестный вид теперь

### C. Области согласования, обещанные архитектурой и планом, в коде нет

`docs/ARCHITECTURE.md:640` требует «once/session/project/global approval
scopes», а рабочий пункт плана `docs/PLAN.md:422` (4.3 Approval and review)
говорит «once/always/reject **with scope**». Код знает только `once`,
`always`, `reject` (`lib/yeah-approval.el:56`); session-, project- и
global-области в `lib/` нет.

**Вердикт: код.** План прямо называет область как часть работы; claim
`approvals-have-reply-kinds` покрывает только нынешние три ответа — то есть
план и код честно расходятся, и разрыв закрывается волной C.

**Закрыто 22 ноября 2026 (волны `wave-c1`, `wave-c2`, `wave-c3`):**  разрыв
закрыт, и закрыт он в коде, а не в документе.  Область стала полем ответа
самой по себе; у каждой области ровно один носитель, и соответствие живёт в
одной таблице (`yeah-perm--carriers`, `lib/yeah-perm.el:143`): `once` не
хранит правила, `run` и `session` держат правила в памяти своего пути,
`project` — в файле проекта, `global` — в файле пользователя.  Словарь ответов
стал словарём областей (`(:once :session :project :global :reject)`), а
старое имя `always` читается как ответ `session` (и не как `global`).
**Текст `docs/ARCHITECTURE.md` §8 приведён к этому коду волной E3**
(2026-11-22).
