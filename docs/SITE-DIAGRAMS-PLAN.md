# Диаграммы для сайта Yeah — разбор и план

> **Статус документа:** предложение, а не задача. Ни одна диаграмма на сайте
> пока не нарисована; этот файл говорит, какие диаграммы нужны, где именно они
> должны стоять и что придётся поменять в тексте.
> Дата разбора: 2026-11-20. Основной источник — код (`lib/`, `plugin/`,
> `site/`) и `docs/ARCHITECTURE.md`; спорные места перечислены в §9.

## 1. Зачем этот документ

Задача: на сайте Yeah вместо одной ASCII-картинки в разделе `*architecture*`
должен быть набор **классических UML-диаграмм**, раскрытых по тексту, а не
собранных в галерею. Форма — классическая UML-нотация, цвет — палитра сайта
(лицо Emacs 30.2 в светлой теме, modus-vivendi в тёмной).

Цель, которую диаграммы должны обслуживать: человек, открывший сайт, должен
за первые два экрана понять **что это, как работает цикл, где оно живёт и с
кем говорит**.

## 2. Что за проект (краткая карта для читателя отчёта)

Yeah — «Yeah, Emacs Agent Harness». Ядро — Emacs Lisp, 65 модулей в `lib/`,
около 17 000 строк. Наружу ядро говорит тремя способами: ACP (агентный
протокол), MCP (протокол инструментов) и мост `emacsclient` к живым буферам
человека. Модель достигается через приватный адаптер gptel; оркестратор
Paseo подключается плагином `plugin/yeah-provider/` (TypeScript), который
поднимает Emacs и говорит с ним по ACP.

Три «размещения» (placements) — `attached`, `service` (основное), `batch` —
пишут одни и те же события в один и тот же журнал.

Ключевое для диаграмм: журнал (`lib/yeah-session.el`) — источник истины, всё
остальное — проекции журнала. Это единственная мысль, которую сайт обязан
донести.

## 4. Дизайн-язык диаграмм

### 4.1 Нотация

Классическая UML 2.x, без изобретений:

* **Прямоугольник с compartments** — компонент или класс; в верхней
  compartments имя, ниже стереотип в «ёлочках» (`«tool registry»`), ниже —
  атрибуты/операции, если нужны.
* **Ромб** — решение; **скруглённый прямоугольник** — действие
  (activity); **эллипс** — состояние; **толстый залитый треугольник** —
  начальное состояние; **двойной круг** — конечное состояние.
* **Сплошная стрелка** — вызов/поток данных; **пунктирная со стрелкой** —
  `«include»`/`«extend»`/реализация; **открытая стрелка** — зависимость.
* **Заметка (note)** — скруглённый прямоугольник со загнутым уголком.

Никаких «модных» скруглений, теней и градиентов внутри самих схем: сайт
прямо запрещает их (`site/README.md:84`), а палитра Emacs — плоская по
определению. Плоские заливки, волосяная линия `1px`, прямые углы у рамок.

### 4.2 Палитра

Палитра сайта уже есть и уже двухуровневая: `--face-*` (лица Emacs 30.2) и
`--fl-*` (font-lock) в светлой теме и в `modus-vivendi`
(`site/styles.css:20–140`). Схемы обязаны использовать эти же переменные, и
тогда обе темы работают без правок и без дублирования картинок.

Раскладка по ролям:

| Роль в схеме | Токен | Зачем |
|---|---|---|
| Фон узла | `--face-default-bg` | буфер — белый в светлой теме, чёрный в тёмной |
| Обводка узла | `--face-divider` | жёсткая линия, «hairline» |
| Текст узла | `--face-default-fg` | основной текст |
| Второстепенный текст (подписи, примечания) | `--face-prose` | серый20 в светлой, fg-dim в тёмной |
| Акцент: стереотип, имя интерфейса | `--fl-keyword` | Purple / `#b6a0ff` |
| Акцент: названия инструментов | `--fl-builtin` | dark slate blue / pink |
| Акцент: названия состояний | `--fl-type` | ForestGreen / `#6ae4b9` |
| Ошибка, запрет, «не достигается» | `--face-error` | Red1 / `#ff5f59` |
| Разрешение, разрешённый путь | `--face-success` | ForestGreen / `#44bc44` |

Правило: **цвет никогда не единственный носитель смысла.** Волнистая линия,
штриховка узла, подпись «(недостижимо)» дублируют любой цвет — сайт уже
требует этого для статусов (`site/README.md:140`).

Подписи — фиксированная ширина (`--font-mono`), как код и ярлыки в Emacs;
поясняющий текст — `--font-proportional`. Это то же правило, что и в
`docs/SITE-DESIGN.md` § «Two typographic families».

### 4.3 Техническая форма: инлайновый SVG

Рекомендация — **SVG прямо в `index.html`**, стилизованный классами из
`site/styles.css`:

* `<img src="…svg">` не подходит: внешний SVG не наследует переменные CSS
  страницы, поэтому тёмная тема не переключится; `<object>` требует отдельного
  документа на тему; PNG не переключается вообще и нечитаем для скринридера.
* Инлайновый SVG наследует `--face-*` и `--fl-*` как есть, работает без
  JavaScript (свойство сайта: «The page is readable with JavaScript
  disabled»), печатается, масштабируется без потери резкости и даёт
  `role="img"` + `<title>`/`<desc>` для доступности.
* Mermaid как рантайм-зависимость исключён: сайт объявляет отсутствие
  зависимостей и сборки (`site/README.md:3–5`). Если Mermaid и будет
  использован — только как инструмент автора, результат кладётся в репозиторий.

Механика: один `<figure class="diagram" data-diagram="d3">` с
`<svg viewBox="…" role="img">`, `<title>`, `<desc>`, `<figcaption>`; стили —
в `styles.css` (правило `.diagram .node { fill: var(--face-default-bg); … }`).
Печать: `@media print` уже гасит chrome кадра — схемы должны остаться
читаемыми, значит, заливки узлов в печати не отключаются.

### D1. Один ход агента — activity, `*readme*`

Заголовок раздела — «Inspect the whole loop», и это буквально просьба о цикле.
Сейчас в разделе три карточки-инварианта и ничего, что показывает движение.

```
        ●
        │ user-prompt
   ┌────▼─────┐
   │ deciding │◄──────────────┐ continue
   └────┬─────┘               │
        │ stream-end           │
   ┌────▼────────┐             │
   │ post-decide │─────────────┘
   └──┬───┬───┬─┘
      │   │   └─ permission-ask ─► ◇ ask the person ─► ◇ allow/deny
      │   │                    (реальный путь: отложенное решение, §9)
      │   └─ no-tool-calls ─► ⊙ completed
      └─ tool-call
   ┌────▼───────┐
   │awaiting-tool│ ──tool-end──► ┌────────────┐
   └────────────┘                │accumulating│
                                  └──┬──────┬──┘
                     budget-overflow ┘      │ budget-ok
                          ┌────────▼──┐     └──► post-decide
                          │compacting │ ──compact-done──► post-decide
                          └───────────┘
```

Элементы: ромбы — решения, скруглённые прямоугольники — действия, жирная
линия вправо — поток «просьба → результат». Отдельно помечены ветки
`error → failed` и `interrupt → interrupted`.

Смысловая нагрузка: читатель видит, что модель **предлагает**, а решает
реестр и политика; что журнал — единственное место, где живёт история; что
вызов инструмента может уйти к человеку за разрешением.

### D3. Emacs-слой — component diagram, `*why-emacs*`

Сейчас раздел состоит из шести пунктов (BUFFERS, INTROSPECT, EDIT,
DIAGNOSE, COMPOSE, RECOVER) без единой картинки — это самое «текстовое» место
на сайте, и оно идеально для схемы «человек ↔ Emacs ↔ агент».

```
 ┌──────────────────┐        ┌───────────────────────┐
 │  Ваш Emacs       │        │  Emacs агента        │
 │  (тот, где вы    │        │  (служебный процесс)  │
 │   работаете)     │        │                       │
 │                  │        │  «introspect»         │
 │  живой буфер ◄───┼────────┼──────► «buffer-read»  │
 │  несохранённый   │ bridge │                       │
 │  текст           │(emacs- │  «elisp-check»        │
 │                  │client) │  «diagnostics»        │
 │  Eglot/Flymake   │        │  «git_status/diff»    │
 └──────────────────┘        └───────────────────────┘
            │                              │
            └──────────► модель ◄──────────┘
```

Мост — единственный путь к живому состоянию, и он **явно одобряемый**: это
опорная мысль раздела, её стоит подписать на самой стрелке.

Отвечает на первый вопрос установщика: «где это будет работать и кто будет

### D5. Состояния прогона — state machine, `*architecture*`

У ядра ровно 12 состояний и 20 ячеек переходов (`lib/yeah-state.el:26`,
`lib/yeah-loop.el:20–45`). Это готовая машина состояний UML, причём
единственная в проекте, которую можно нарисовать без домыслов.

**Осторожно: рисовать все 20 ячеек нельзя** — 7 из них ядро никогда не
проходит (см. §9, находка A). Схема должна показывать путь, который
существует, а объявленное, но недостижимое — отдельной сноской. Рисунок,
на котором 12 состояний выглядят одинаково достижимыми, был бы ложью, а
проект такие лжи не публикует.

### D6. Фиксированная точка Y — activity, `*vision*`

### D7. Уровни проверки — activity с зонами, `*Messages*`

Четыре уровня из `docs/ARCHITECTURE.md` §10 (unit → contract/canary →
integration → live) плюс явная граница «что доказано, а что нет». Раздел
Status — единственное место, где читатель ищет «а это правда?», и сейчас
там только два списка текстом.

### D8. Пакеты кода — package diagram, `*development*`

`lib/` разложен по девяти пакетам (журнал и проекции; управление прогоном;
адаптер модели; инструменты и реестр; права и согласования; протоколы и
провод; интерфейс и продукт; делегация и субагенты; размещения и обвязка).
Схема отвечает на вопрос «где что лежит» и рисуется один раз на весь
репозиторий — её полезно держать в `docs/` рядом с `ARCHITECTURE.md`, а на
сайт поставить укрупнённую версию без лишних модулей.

## 6. Что НЕ надо рисовать

| Не рисуем | Почему |
|---|---|
| Класс-диаграмма всех структур Elisp | Новичку нечего извлечь; карта модулей (D8) полезнее |
| Диаграмма классов реестра инструментов (23 инструмента) | Перегруз; достаточно таблицы семейств инструментов текстом |
| Диаграмма последовательности каждого метода ACP | 10 методов — это документация протокола, а не объяснение устройства |
| ER-диаграмма | Реляционной модели данных нет; журнал — append-only поток событий, это лучше показывает D2 |
| Диаграмма классов «человек ↔ Emacs» | Emacs — не класс; это уровень размещения, его место — D4 |
| Полная таблица 20 переходов на стене | Семь ячеек недостижимы (A); таблица переедет в `docs/`, на сайт — путь |

## 7. Размещение: что вставить и что поправить в тексте

Точные места — по `site/index.html`.

### `*scratch*` (hero, 217–301) — без изменений

Лог сессии остаётся: он human-readable и работает как иллюстрация. Но
подписи инструментов в нём сейчас `Read`, `Edit`, `Build` (заглавными), а в
ядре имена машинные и строчные: `read`, `edit`, `write`, `bash`,
`introspect`, `diagnostics`, `git_status`, `git_diff`, `git_commit`,
`todo_add`, `todo_update`, `todo_list`, `buffer-read`, `elisp-check`,
`job-status`, `job-read`, `job-cancel`, `delete`, `delegate`,
`delegate-result`, `finish`.

Решение: **лог в hero не трогаем** — он помечен как illustrative, и
заглавные буквы там работают как прозаический текст. Но в D1/D3 подписи
инструментов даём машинные, и в подписи к рисунку пишем одну фразу: *«имена
инструментов в схеме — те, что зовёт модель»*. Так читатель не решит, что
`Read` и `read` — разные инструменты.

### `*vision*` (304–353) — добавить D6

* Вставка: `<figure class="diagram" data-diagram="d6">` после блока

## 8. Порядок работы и критерии приёмки

Рекомендуемая очередность — по одной волне на диаграмму, каждая волна
закрывается проверкой в браузере, как это делается для остального сайта
(`docs/SITE-DESIGN.md` § «The verification»).

1. **Волна 1 — D2.** Замена ASCII-рисунка: это видимое изменение, его
   видят все, и оно задаёт язык остальным схемам.
2. **Волна 2 — D1.** Activity цикла в `*readme*`.
3. **Волна 3 — D3.** Emacs-слой в `*why-emacs*`.
4. **Волна 4 — D4.** Размещения в `*install*`.
5. **Волна 5 — D5.** Машина состояний (после того, как решено, как
   показывать недостижимые ячейки).
6. **Волна 6 — D6, D7, D8.** По желанию и по бюджету.

Критерии приёмки (общие для всех волн):

* схема читается в светлой и в тёмной теме, в 1440 px и в 420 px;
* у каждой схемы есть `<title>`, `<desc>` и подпись под рисунком;
* ни один цвет не единственный носитель смысла;
* контраст текста схемы — не ниже 4.5:1 к своему фону;
* схема печатается: `@media print` не убивает её;
* страница остаётся читаемой без JavaScript;
* режим кадра не меняется: ни один новый буфер, ни одна новая вкладка;
* для D5 — есть проверка, которая сверяет подписи на схеме с
  `yeah-loop--raw-transitions` и падает, если они разошлись (это тот же
  принцип «контроль, который может укусить», что и в `tests/checks/`).

## 9. Противоречия, найденные при чтении кода

Проект считает расхождение кода и документа находкой, а не поводом тихо
поправить документацию (`AGENTS.md`, «Read first»). Ниже — три расхождения,
которые прямо влияют на рисунки. Их стоит завести как открытые пункты работы,
а не решать молча.

**A. Восемь ячеек машины состояний ядро никогда не проходит.**
`lib/yeah-loop.el:20–45` объявляет 20 переходов, но рантайм вызывает
`yeah-turn--tick` только с десятью метками: `user-prompt`, `stream-end`,
`tool-call`, `no-tool-calls`, `continue`, `tool-end`, `budget-ok`,
`budget-overflow`, `compact-done`, `error` (`lib/yeah-turn.el:304, 610–611,
662–664, 684–685, 717, 844–846, 902, 1005, 1027, 1347`). Метки
`permission-ask`, `ask-user`, `interrupt`, `timeout`, `answer`,
`rate-relief`, `tick-resume` не вызываются нигде в `lib/`. Значит,
состояния `awaiting-user-permission`, `awaiting-user-input`,
`blocked-on-rate` и `interrupted` недостижимы через таблицу: разрешение
откладывается (`yeah-approval-resolve`, `lib/yeah-approval.el:232`, вызов —
`lib/yeah-turn.el:393`), прерывание и «failed» ставятся напрямую
(`lib/yeah-turn.el:201–207, 306, 1376`). **Влияние на сайт:** D5 нельзя рисовать «как объявлено» — это будет
ложью о работающей системе. Либо рисовать достижимый путь, либо объявить
это в открытом пункте.

**B. У описания инструмента нет полей, которые требует ARCHITECTURE.md.**
`docs/ARCHITECTURE.md:535–548` перечисляет «risk/capability classification»,
«shared/exclusive or resource-lock declaration», «timeout and output limits».
В коде спецификация инструмента — это `:name`, `:description`, `:input`,
`:handler` плюс необязательные `:kind`, `:concurrency`, `:async`
(`lib/yeah-tools.el:104–133`). Поля риска, блокировки ресурса, таймаута и
лимита вывода нет; риск выводится из `:kind` и списка меняющих мир инструментов
(`lib/yeah-perm.el:96–97`), лимит вывода живёт в `lib/yeah-result.el:23`,
таймауты — в аргументах инструментов. **Влияние на сайт:** если нарисовать
композицию «Tool Specification» с этими compartments, схема разойдётся с
документом; нужно либо привести документ в порядок, либо рисовать реальные
поля.

**C. Области согласования, обещанные архитектурой, в коде нет.**
`docs/ARCHITECTURE.md:640` требует «once/session/project/global approval
scopes». Код знает только `once`, `always`, `reject`
(`lib/yeah-approval.el:56`). Ни session-, ни project-, ни global-области в
`lib/` нет. **Влияние на сайт:** подпись «один раз / на сессию / на проект /
навсегда» была бы выдумкой; на схеме D1/D2 подписывать можно только то, что
есть.

**D. Мелочь, но заметная для читателя.** На сайте имена инструментов
заглавными (`Read`, `Edit`, `Build`), в ядре — строчными (`read`, `edit`,
`finish`); `build` — это не инструмент, а профиль прав
(`lib/yeah-perm.el:106`). В схемах имена должны быть машинными.

## 10. Что осталось непроверенным

* Схемы не нарисованы; этот документ описывает, **что** рисовать, а не
  **как** будет выглядеть готовый результат. Геометрия (число узлов на
  строку, переносы подписей) определяется на этапе рисования и должна быть
  проверена в браузере на 420 и 1440 px.
* Счётчики в разделе Status (`331 / 331`, `47`) не перепроверялись запуском:
  правило сайта требует брать числа из реального прогона, а не из памяти.
* Расхождения A–C не проверялись запуском тестов: вывод сделан чтением кода
  и подсчётом мест вызова. Их стоит подтвердить или опровергнуть до того, как
  схема D5 будет нарисована.
* Не проверено, как схемы выглядят в режиме «Toggle Frame Chrome»
  (`site/script.js`, `body.chrome-off`) и при `prefers-reduced-motion`.
